# Epistemic Hierarchy Audit — AeroGrid-XAI

**Audit date:** 2026-10-14
**Repository state:** `main` at commit `9620ac4` (PR #91)
**Sprint task:** s10-3 (Epistemic hierarchy audit)
**Related:** P34 (Sprint 7 s7-7 / s7-9 partial), Section 21 of the specification.
**Deliverable:** this document; P34 status updated accordingly.

## 1. Claim under audit

Specification Section 21 states that every output artifact (chart,
report, API response, decision explanation) generated by the platform
must be tagged with which of seven evidentiary categories it belongs
to, and that the software never presents a simulation result, an AI
prediction, or a formal verification result as if it were a physical
measurement.

The audit's questions:

1. Which UI elements render output, and do they carry an epistemic tag?
2. Which API responses carry an epistemic tag?
3. Does the code base exercise all seven Section 21 categories?
4. Where tagging is absent, is the absence intentional (non-scientific
   output) or a genuine gap?

## 2. The seven Section 21 categories

From the specification Rev. 6, Section 21, ordered strongest to
weakest evidentiary status. The frontend type union
`EpistemicTag` (`frontend/src/components/EpistemicBadge/epistemic.ts`)
enforces this at compile time.

| Level | Tag | Meaning | Band |
|---|---|---|---|
| 1 | `physical_measurement` | Real hardware test result | verified |
| 2 | `validated_physical_model` | Model fit to measurements | verified |
| 3 | `estimated_model` | First-principles, not validated | modelled |
| 4 | `simulation_result` | Digital Twin output | modelled |
| 5 | `ai_prediction` | Tier 2 surrogate with uncertainty | predicted |
| 6 | `formal_verification_result` | SAT/UNSAT against PWL encoding | predicted |
| 7 | `hypothetical_scenario` | User what-if, no real-world claim | hypothetical |

## 5. Findings

### F-1 — `/orbital/*` endpoints do not carry an epistemic tag

The three orbital endpoints return physics-model outputs: a list of
satellites from a TLE catalog, a time-series position/velocity trace
from SGP4 propagation, and a visibility-window computation. Under
Section 21, SGP4 propagation against a TLE is a `validated_physical_model`
(category 2): the propagator is the industry-standard algorithm, and
its accuracy against a reference at TLE epoch is verified
(`test_sgp4_reference.py`). The visibility computation is
`simulation_result` (category 4), since it is derived output of the
model, not a measured quantity.

**Impact.** A client consuming `/orbital/*` over HTTP receives no
Section 21 tag. The frontend panel that renders it (`Globe`) wraps the
whole panel in `simulation_result` — a conservative tag that is
truthful but does not distinguish the propagator's
`validated_physical_model` status. The result is a **partial** gap:
the UI is tagged, the API is not.

**Remediation.** Adding an `epistemic_tag` field to the three response
models is a small code change. It has **not** been made in this PR. The
reason: tagging requires deciding, per endpoint, which of category 2
(`validated_physical_model`) or category 4 (`simulation_result`) is
correct. That decision is a modelling one, not a documentation one, and
it interacts with P21 (the Kruse-Kim coefficients used in the
visibility path have not been cross-checked against the source). The
decision is recorded here as a follow-up, tracked as **F-1** in the
roadmap.

### F-2 — Only one of the seven Section 21 categories is exercised

Across the whole codebase, the only tag emitted is
`simulation_result` (with the single `tier1_decision_trace` value
described in §4.1, which is scope-equivalent). The other six
categories — `physical_measurement`, `validated_physical_model`,
`estimated_model`, `ai_prediction`, `formal_verification_result`,
`hypothetical_scenario` — are **defined** in the frontend type union
and rendered by `EpistemicBadge`, but no production code path emits
them.

**Impact.** The tagging infrastructure has not been exercised against
the full range of the Section 21 hierarchy. A regression in the
rendering of, say, `formal_verification_result` would not be caught by
an integration test, because no feature currently emits that tag. The
`EpistemicBadge.test.tsx` unit tests do exercise every tag (the badge
is rendered for all seven in the App landing section), so the component
itself is covered; the **end-to-end flow from an API response to a
tagged UI element** is only exercised for `simulation_result`.

**Remediation.** Not in this PR. The gap is inherent to the current
system: the platform's production outputs at this commit are all
simulation results and Tier 1 traces. Categories like
`formal_verification_result` will be exercised when a UI panel renders
Z3 SAT/UNSAT verdicts directly (a Sprint 11 candidate); `ai_prediction`
will be exercised when a Tier 2 surrogate's interval is displayed
directly in the UI. Both are legitimate future features, and the audit
records them as **open** rather than as defects.

### F-3 — The `epistemic_tag` for the charge decision is a domain-specific
string, not a Section 21 category name

`explain.py` defines `EPISTEMIC_TAG = "tier1_decision_trace"`. This is
not one of the seven Section 21 literal strings. It is a
**scope-equivalent** label: the constant's docstring states that the
content is "a record of the Tier 1 model's own arithmetic, not a
physical-reality claim", which is category 4 (`simulation_result`) in
the Section 21 taxonomy.

**Impact.** A strict reading of Section 21 would require
`epistemic_tag` to be one of the seven category names. The current
value is truthful but does not conform to the literal enumeration. A
downstream consumer that switches on `epistemic_tag` against the seven
categories would not match `tier1_decision_trace`.

**Remediation options.**

- (a) Change `EPISTEMIC_TAG` to `"simulation_result"` and move the
  "tier1_decision_trace" distinction into a separate field
  (`sub_tag` or `scope`).
- (b) Keep the tag as-is and document it as a Section 21-scoped
  subtype of category 4.

Neither change is made in this PR. The decision interacts with the API
contract, the frontend rendering, and any external clients. It is
recorded as a follow-up.

### F-4 — The seven-category contract is enforced on the frontend, not the backend

The frontend `EpistemicTag` union rejects unknown tags at compile time.
The backend response models declare `epistemic_tag: str`, with no
constrained set. A backend change that emitted `"made_up_tag"` would
compile and pass CI; the frontend would then render an untagged box for
that response (or the union check would fire at runtime, depending on
how the string is passed to `EpistemicBadge`).

**Impact.** The Section 21 contract is enforced at the type level on
one side of the wire and not the other. This is a defence-in-depth
gap, not a live defect.

**Remediation.** A `Literal` type or an `Enum` for `epistemic_tag` on
the backend response models would close the gap. Recorded as a
follow-up.

## 6. P34 status

`ROADMAP_STATUS.md` P34 reads: *"Sprint 7 s7-7 and s7-9 are partial:
the badge infrastructure and per-panel tagging exist, but no formal UI
audit has been done."*

**P34 is closed by this document.** The audit is now written. Its
substantive finding is that the infrastructure is complete and correct
for the outputs the platform currently produces, and that the four
findings above are about *coverage of the seven categories* and
*backend type enforcement*, not about missing tags on shipped outputs.

## 7. What this audit does not do

- **It does not change code.** Findings F-1 through F-4 are recorded
  for follow-up. None of them is a live defect on a shipped output
  path.
- **It does not audit SaaS responses.** The SaaS endpoints are
  administrative, not scientific; the Section 21 rule applies to
  scientific outputs, and the audit records their intentional absence
  rather than treating it as a gap.
- **It does not audit WebSocket message schemas beyond the one line
  identified.** The `WS /telemetry/stream` payload carries
  `epistemic_tag = "simulation_result"`; a full schema audit of the
  stream is out of scope.

## 8. Certification

Within the scope of §1:

- Every top-level UI feature panel that renders an output wraps it in
  `TaggedOutput` with an explicit Section 21 category. The three child
  components that are not individually tagged render inside a tagged
  parent.
- Every scientific backend endpoint except the three `/orbital/*` routes
  carries an `epistemic_tag` field on its response model.
- The `EpistemicBadge` component enforces the seven-category union at
  the TypeScript type level and is unit-tested against all seven.
- Four findings (F-1 through F-4) are recorded with remediation plans;
  none is a live defect on a shipped output path. P34 is closed.
